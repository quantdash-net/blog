做量化研究或搭建交易工具，第一步往往不是写策略，而是选数据源。行情数据 API 的介绍页大多写得很像：都说覆盖全、速度快、好接入。真正决定后续体验的，是那些介绍页上不太显眼的细节：分钟线覆盖哪些市场、复权怎么算、"实时"到底指什么、超频之后会发生什么、换数据源要改多少代码。

这篇文章不给任何产品打分，而是整理一套**可以复用的对比维度**。你可以拿它去评估任何一家数据服务，包括 QuantDash。文中凡是提到 QuantDash 的地方，都只引用 [QuantDash 中文文档](https://docs.quantdash.net/zh-Hans) 和 [官网](https://quantdash.net/) 的原文口径，作为"文档里应该能找到什么"的示例。

## 先想清楚：你的数据需求是什么

在比较之前，先把自己的需求写下来。不同用途对数据的要求差别很大：

- **日线级研究和回测**：关心历史深度、复权方式、停牌和除权处理，对时效要求不高。
- **盘中监控和选股**：关心全市场快照能否一次拉取、快照多久更新一次。
- **日内策略研究**：关心分钟线的周期、覆盖的市场和历史长度。
- **工具和看板类应用**：关心接入是否简单、字段是否稳定、调用频率是否够用。

需求不清楚时，很容易被"覆盖 N 个市场""支持 M 种数据"这样的数字带着走，最后发现真正要用的那一项恰好不在套餐里。

下面这张表可以直接复制到你的选型文档里，每一行都对应一个需要在文档或试用中确认的问题。

| 维度 | 要问的问题 | 如何验证 |
| --- | --- | --- |
| 市场覆盖 | 覆盖哪些市场和品种？A 股是否含北交所？ETF 是否单独列出？ | 看文档的代码格式表，实际请求每个市场的样例代码 |
| 数据类型 | K 线、快照、盘口、分时、除权因子、元数据分别有没有？ | 看接口列表，逐个调用确认字段 |
| 周期与粒度 | 分钟线有哪些周期？分钟线覆盖哪些市场？ | 看周期枚举和每个周期的适用市场说明 |
| 接入方式 | 有没有 REST？有没有官方 SDK？鉴权方式是什么？ | 用最小示例从零跑通一次，记录耗时 |

接下来逐项展开。

## 维度一：市场覆盖，看到"代码格式"这一层

"支持 A 股、港股、美股"是最粗的一层信息。要往下追问两层：

1. **具体到交易所和品种**。A 股是否包含沪、深、北三个交易所？ETF 是否可查？
2. **代码怎么写**。不同服务的代码格式差异很大，有的用前缀，有的用后缀，有的用纯数字加市场参数。代码格式决定了你的标的池和本地数据库怎么设计。

以 QuantDash 为例，文档的 REST API 说明里给出了统一的 `{代码}.{交易所后缀}` 格式：`.SH`（上交所）、`.SZ`（深交所）、`.BJ`（北交所）、`.US`（美股）、`.HK`（港股），例如 `600519.SH`、`AAPL.US`、`00700.HK`。文档首页写明覆盖 A 股（沪深京）、ETF、美股、港股。这种信息在评估阶段就应该能直接在文档中找到。

另外要确认：**不同市场是否需要分别开通**。QuantDash 的文档 FAQ 写的是"不同市场需分别订阅"。这会直接影响成本测算，后文成本部分再展开。

## 维度二：数据类型，逐项列清单

常见的行情数据类型包括：

- **历史 K 线（OHLCV）**：开高低收、成交量、成交额。
- **实时快照**：最新价、昨收、涨跌幅、成交量等。
- **盘口深度**：买卖档位价格和数量。
- **日内分时**：当日分钟级走势。
- **除权因子**：用来自行计算复权价格。
- **标的元数据**：名称、交易所、类型、上市日期等。

评估时建议做一张清单，把你需要的每一项都打上"必需 / 可选 / 不需要"，再对照文档逐项确认。QuantDash 文档 FAQ 列出的数据类型是：实时行情快照、日/周/月 K 线、分钟 K 线（1m/5m/15m/30m/60m）、日内分时、五档盘口、除权因子、标的元数据。

需要特别注意**"支持"的范围**。比如同样是 K 线，日线和分钟线的覆盖市场可能不同。QuantDash 文档首页写明：日线类周期（`1d`、`1w`、`1M`、`1Q`、`1Y`）覆盖 A 股、美股、港股，分钟线（`1m`、`5m`、`15m`、`30m`、`60m`）标注为 A 股。如果你的策略需要港股或美股的分钟级历史，这一条就要单独确认。

## 维度三：复权方式，回测结果差异的常见来源

复权处理不一致，是"同一个策略在两个数据源上回测结果不一样"的常见原因之一。评估时至少确认三件事：

1. 支持哪几种复权：前复权、后复权、不复权。
2. 复权算法：比例复权（乘法）还是差值复权（加减法）。
3. 默认值是什么：不传参数时返回的是哪一种。

QuantDash 的 Python SDK 文档列出了 5 种 `adjust` 取值：`forward`（前复权-比例复权，默认）、`backward`（后复权-比例复权）、`forward_additive`（前复权-差值复权）、`backward_additive`（后复权-差值复权）、`none`（不复权），并说明比例复权适合计算收益率，差值复权适合观察绝对价差。另外文档提供除权因子接口，需要自己控制复权逻辑时可以直接拿因子计算。

不管用哪家数据，**在代码里显式写出复权参数**，不要依赖默认值，这样换数据源时更容易发现差异。

## 维度四：接入方式，从零跑通一次

接入方式决定了团队的上手成本。可以从这几个方面比较：

- **协议**：REST、WebSocket 还是专有客户端。REST 的好处是任何语言都能直接调用。
- **SDK**：有没有官方维护的 SDK，是否能直接返回 DataFrame。
- **鉴权**：Key 放在请求头还是 URL 参数，是否支持环境变量。
- **返回格式**：行式还是列式，字段命名是否稳定。

最实用的评估方法是：**在一个新环境里，从注册到拿到第一条数据，完整走一遍**，记下每一步卡在哪。

以 QuantDash 为例，文档给出的接入方式是 RESTful API 加 Python SDK。REST 的 Base URL 是 `https://api.quantdash.net`，在请求头 `X-API-Key` 中携带 Key；SDK 通过 `pip install quantdash` 安装，支持 Python 3.9+，可以通过环境变量 `QUANTDASH_API_KEY` 读取 Key。K 线接口的返回是列式结构（每个字段一个数组，下标对应同一根 K 线）。

一个最小的跑通脚本大概是这样（Key 从环境变量读取，不要写进代码）：

```python
import os
from quantdash import QuantDash

qd = QuantDash(api_key=os.environ["QUANTDASH_API_KEY"])

for symbol in ["600519.SH", "00700.HK", "AAPL.US"]:
    df = qd.klines.get(symbol, period="1d", count=5, adjust="forward", to_dataframe=True)
    print(symbol, len(df), df["trade_date"].iloc[-1])
```

评估其他服务时，也可以写一个结构相同的脚本，对比代码量和需要处理的特殊情况。

## 维度五：频率口径，区分"刷新频率"和"响应延迟"

这是最容易被混淆的一项。"实时""低延迟"至少可能指三件不同的事：

| 概念 | 含义 | 影响什么 |
| --- | --- | --- |
| 快照刷新频率 | 服务端的行情快照多久更新一次 | 你最快多久能看到一次新价格 |
| 接口响应时间 | 一次请求从发出到收到返回要多久 | 程序等待多久、单位时间能发多少次请求 |
| 调用频率限制 | 单位时间内允许发多少次请求 | 轮询策略和批量方式 |

这三者互相独立：响应很快的接口，背后的快照也可能是每隔几秒才更新一次；反过来，快照刷新得很快，如果限流很严，你也拿不到每一次更新。**评估时一定要分别找到这三项的原文描述**，不要把其中一个数字当成另一个用。

QuantDash 文档 FAQ 对快照的描述是："实时行情快照约 3 秒刷新一次。K 线数据盘中实时更新。"这是**刷新频率**口径。至于限流，REST API 文档列出了 429 状态码（请求频率超限），具体额度以账户所在方案为准。

## 维度六：稳定性与错误处理

稳定性很难在试用期内测出来，但错误处理的设计可以提前看清楚：

- 错误码是否有文档，能否区分"Key 无效""没有权限""超频"。
- 超频时是否告诉你应该等多久。
- SDK 是否内置重试，对哪些错误重试。

QuantDash 的 REST 文档列出了三个主要错误码：401（API Key 无效或缺失）、403（无权限，套餐不包含该功能或市场）、429（请求频率超限）。接口定义中，429 的返回体包含 `retry_after_ms` 字段，表示建议等待时间（毫秒）。能区分 401 和 403，排查问题时就能很快判断是 Key 的问题还是套餐权限的问题。

建议在评估脚本里故意制造几种错误：传错 Key、传一个不存在的代码、短时间连续请求，看返回是否清晰、文档是否对得上。

## 维度七：合规与授权

这一项常被忽略，但对要做产品的团队最关键：

- 数据能否用于个人研究以外的场景？
- 能否把数据展示给你的用户？能否转售或再分发？
- 服务协议中对使用范围、存储期限有没有限制？

不同服务的条款差别很大，本文不做概括。唯一的建议是：**读服务协议原文**（QuantDash 的服务协议在官网页脚），有任何不确定的地方，书面询问服务方并保留回复。

## 维度八：成本模型与迁移成本

比较价格前，先搞清楚计费单位：

- 按**市场**订阅，还是按**功能**订阅，还是按**调用量**计费？
- 免费额度包含哪些市场和数据类型？
- 升级时已有订阅怎么处理？有没有退款政策？

QuantDash 官网定价页的 FAQ 写明：注册即获免费额度，包含 A 股实时行情和日 K 线；不同市场独立订阅、按需组合；升级时直接购买新方案，系统自动合并所有活跃订阅的权限；所有付费方案享 7 天无理由退款（扣除支付手续费）。具体价格和各方案的额度以定价页实时显示为准，本文不引用具体数字。

**迁移成本**同样应该算进去。建议在自己的代码里加一层很薄的数据访问层，把"取 K 线""取快照"封装成自己的函数，内部再调用具体的数据服务。这样以后无论换不换数据源，策略代码都不需要改动。

## 一个可执行的评估流程

把上面的维度串起来，一个半天就能完成的评估流程是：

1. **写需求清单**：市场、数据类型、周期、历史长度、时效要求、预算。
2. **读文档**：对照维度总览表逐行填写，找不到原文的项标记为"待确认"。
3. **跑通最小脚本**：每个候选服务都用结构相同的脚本，覆盖你需要的每个市场。
4. **核对数据**：抽几个有除权、停牌的标的，比较复权后价格和交易日是否一致。
5. **测试错误处理**：错 Key、错代码、超频各试一次。
6. **读协议和定价**：确认使用范围和计费方式，算出一年的成本。
7. **决策并留档**：把评估表和脚本保存下来，下次复评可以直接复用。

## 问答小结

**问：选行情数据 API 时，最先要确认的是什么？**
答：先确认自己的需求，再看市场覆盖是否细到交易所和代码格式，以及分钟线等关键数据的覆盖市场。介绍页上的"覆盖多市场"不等于每种数据都覆盖每个市场。

**问："实时行情"和"低延迟"是一回事吗？**
答：不是。快照刷新频率、接口响应时间和调用频率限制是三个独立指标。例如 QuantDash 文档写的是"实时行情快照约 3 秒刷新一次"，这是刷新频率口径，不能当作接口响应时间来理解。

**问：为什么两个数据源回测结果会不一样？**
答：常见原因是复权方式不同（前复权/后复权、比例/差值）和默认值不同。在代码中显式写明复权参数，并抽样核对除权日前后的价格。

**问：多市场数据的成本怎么估算？**
答：先确认计费单位是按市场、按功能还是按调用量，再看免费额度覆盖范围。QuantDash 官网写明不同市场独立订阅，注册免费额度包含 A 股实时行情和日 K 线。

**问：怎样降低以后更换数据源的成本？**
答：在策略代码和数据服务之间加一层自己的数据访问函数，并保留评估脚本，换源时只需改这一层。
